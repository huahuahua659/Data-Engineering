# 电商订单数据探索

用一个脚本把两张表的全貌过一遍：字段含义、缺失、异常、表关系、汇总口径是否对得上。

## 数据

| 文件 | 规模 | 说明 |
|------|------|------|
| `order.csv` | 382,287 行 × 24 列 | 订单明细（事实表），2024-01-01 ~ 2025-01-02 |
| `user.csv` | 98,673 行 × 16 列 | 用户主表（维度表），1 行 = 1 个用户 |

两表通过 `user_id` 关联，无孤儿订单；6,269 名用户注册后没有下单。数据本身是模拟数据，`description` 字段是模板拼接（"维生素C与维生素C复配"这类），省份 GDP 也与真实值不符，不要当真实业务结论用。

## 运行

```bash
python data_exploration.py --data-dir ../data --out outputs/data_exploration_report.txt
```

`--data-dir` 默认脚本同级的 `data/`，`--out` 默认 `outputs/data_exploration_report.txt`。报告里只写文件名，不带本机绝对路径。

## 关键发现

1. **缺失**：`promotion_type` 空值 69.91%（空 = 无促销，是有意义的缺失，不能直接删）；`gender` 有约 10% 的 `Unknown`，属隐性缺失。
2. **汇总字段对不上**：`user` 表的 `total_purchase_times` 与订单表实际聚合值不一致的用户占 83.4%，`total_purchase_amount` 差异超过 1 元的占 100%。说明两张表是独立口径，建模时不能混用——后续的特征工程也确实没用这两个字段。
3. **金额逻辑**：无促销时 `amount = price × quantity`；有促销时折扣固定——Coupon 10%、FlashSale 20%、FullDiscount 15%。约 30% 的订单金额不等于原价乘积，是促销造成的，不是脏数据。
4. **集中度极高**：GMV 6.56 亿元，3C 电子占 87%（小米单品牌 2.33 亿），客单价 1,716 元。这种分布是模拟数据生成规则造成的，真实电商不会这么偏。
5. **用户表是另一套数**：`user` 表的金额、次数与订单明细完全对不上，更像是由独立脚本生成的画像，而非订单的历史汇总。

## 局限

- 3σ 异常检测用在了 `quantity`（取值 1~3）上，标出的 19,055 行是误报——离散小范围变量没有"3σ 异常"的概念。`amount`、`price` 的检测结论也只说明有长尾，不能直接当异常。
- 只做了单表统计和两表关系核对，没有做时间序列、复购、漏斗等进一步分析。
